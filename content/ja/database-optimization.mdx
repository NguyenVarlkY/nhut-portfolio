# Deep Dive：データベース最適化の深層

データベースの最適化は「試行錯誤」ではありません。データがディスク上でどのように保存・取得・ロックされるかを扱う科学です。以下は詳細な技術解説です。

## 1. B-Tree の内部構造：データ構造を理解する
インデックスは単なるリストではありません。
- **B-Tree 構造：** 平衡木であり、検索・挿入・削除を $O(\log n)$ の時間で行えます。
- **ページ分割（Page Split）：** ノードが満杯になると、データベースはそのノードを分割しなければならず、I/O コストがかかります。必要がなければ、ランダムな `UUID` を主キーにするのは避けましょう。`Integer Auto-increment` に比べてインデックスの断片化がずっと大きくなります。
- **Fill Factor：** ページの充填率を調整して、読み書きの性能を最適化します。

## 2. クエリプランナーと実行計画
常に `EXPLAIN (ANALYZE, BUFFERS)` を使って次の点を確認しましょう：
- **Sequential Scan と Index Scan：** 数百万行のテーブルでの seq scan は大惨事です。
- **コスト見積もり：** PostgreSQL/Oracle は統計情報（statistics）を使って最適な経路を推測します。統計が古い（stale）と、プランナーは誤った経路を選びます。
- **Nested Loop と Hash Join：** 大きなデータセットでは、通常 Hash Join の方が Nested Loop より高速ですが、より多くのメモリを使います。

## 3. 高度な SQL テクニック
### 3.1. 大量データの扱い
- **ページネーション：** 非常に大きなデータ（数百万行）に `OFFSET/LIMIT` を使ってはいけません。`OFFSET` は手前のすべての行をスキャンする必要があるからです。代わりに **Keyset Pagination**（前のページの最後の行の列値を基準にする方式）を使いましょう。
- **パーティショニング：** 巨大なテーブルは時間で分割（例：月ごとのパーティション）し、クエリを高速化して古いデータを管理しましょう。

### 3.2. 同時実行制御
- **ロック：** `Row-level locking` と `Table-level locking` の違いを理解しましょう。
- **デッドロック：** 高い同時実行性の環境でデッドロックを避けるには、常に決まった順序でリソースを更新しましょう。

## 4. 全文検索（FTS）
`LIKE '%keyword%'` は使わないでください。
- **なぜ？** 通常のインデックス（B-Tree）を利用できないからです。
- **解決策：** **GIN/GiST インデックス**（Postgres）を使うか、大規模な拡張性や複雑な検索（あいまい検索、ステミング）が必要なら **ElasticSearch** を導入しましょう。

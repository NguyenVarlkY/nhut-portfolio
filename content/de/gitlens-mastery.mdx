# GitLens meistern: Den Git-Workflow optimieren

GitLens ist eine der beliebtesten Erweiterungen für Visual Studio Code und erweitert die in die IDE integrierte Git-Unterstützung erheblich. Es macht VS Code zu einem leistungsstarken Werkzeug, um die Codehistorie zu verstehen, Änderungen nachzuverfolgen und effektiv im Team zu arbeiten.

## Warum GitLens?

### 1. Die Codehistorie sofort verstehen
- Sehen, wer welche Codezeile geändert hat (Blame-Annotationen)
- Kontext und Gründe hinter jeder Änderung verstehen
- Nachverfolgen, wie sich eine Datei im Laufe der Zeit entwickelt hat

### 2. Effizienter arbeiten
- Ohne den Editor zu verlassen auf die Commit-Historie zugreifen
- Verschiedene Versionen einer Datei vergleichen
- Die Git-Historie visuell durchsuchen und durchstöbern

### 3. Bessere Zusammenarbeit im Team
- Klar erkennen, wer an welchen Teilen der Codebasis arbeitet
- Mögliche Probleme im Code-Review erkennen
- Wichtigen Kontext erhalten, wenn man mit unbekanntem Code arbeitet

## GitLens installieren und konfigurieren

### 1. Grundinstallation
- VS Code öffnen
- Zu Extensions wechseln (Strg+Umschalt+X)
- Nach „GitLens“ suchen
- Auf Install klicken

### 2. Grundkonfiguration
GitLens lässt sich über Settings (Strg+,) → Suche nach „GitLens“ konfigurieren

#### Empfohlene Konfiguration:
```json
{
  "gitlens.blame.toggleModeKey": "alt+ctrl+b",
  "gitlens.hovers.currentLine.over": "line",
  "gitlens.hovers.currentLine.enabled": true,
  "gitlens.advanced.blame": {
    "toggleModeKey": "alt+ctrl+b"
  },
  "gitlens.codeLens.authors.enabled": true,
  "gitlens.codeLens.recentChange.enabled": true,
  "gitlens.codeLens.recentChange.location": "after",
  "gitlens.keymap": "alternate"
}
```

## Die wichtigsten Funktionen von GitLens

### 1. Blame-Annotationen
- Zeigt direkt im Editor, wer jede Codezeile zuletzt geändert hat
- Beim Überfahren mit der Maus Commit-Details anzeigen
- Per Klick den Commit in der Historie öffnen

#### So nutzt du sie:
- Blame ein-/ausschalten: `Alt+Strg+B`
- Blame-Modus wechseln: über die Statusleiste unten
- Darstellung in den Einstellungen anpassen

### 2. Code Lens
- Zeigt an jeder Funktion/Klasse Informationen zum letzten Commit
- Zeigt, wie viele Autoren zur Datei beigetragen haben
- Bietet Schnellaktionen wie Commit anzeigen oder neuen Branch erstellen

#### Arten von Code Lens:
- **Authors**: Listet die Autoren auf, die zur Datei beigetragen haben
- **Recent Change**: Zeigt den letzten Commit, der diesen Code geändert hat
- **Revisions**: Zeigt, wie oft die Funktion/Klasse geändert wurde

### 3. Commit-Historie und Suche
- Schneller Zugriff auf die Commit-Historie des Repositorys
- Commits nach Stichwort, Autor oder Datum suchen
- Commits nach Branch, Tag oder anderen Kriterien filtern

#### So greifst du darauf zu:
- GitLens-Ansicht öffnen: `Strg+Umschalt+P` → „GitLens: Focus on Repository View“
- Oder auf das GitLens-Symbol in der linken Seitenleiste klicken

### 4. Versionen vergleichen
- Die aktuelle Datei mit jeder beliebigen Version aus der Historie vergleichen
- Zwei verschiedene Branches vergleichen
- Die Unterschiede zwischen zwei bestimmten Commits ansehen

#### So geht's:
- Im Explorer mit der rechten Maustaste auf eine Datei klicken → „GitLens: Open Changes“
- Oder in der GitLens-Ansicht → Commit auswählen → „Compare with Working Tree“

### 5. Historie erkunden (History Exploration)
- Commits nach Inhalt durchsuchen, nicht nur nach Metadaten
- Herausfinden, wann eine bestimmte Codezeile hinzugefügt, entfernt oder geändert wurde
- Code verfolgen, der zwischen Dateien verschoben wurde

#### So geht's:
- In der GitLens-Ansicht → auf das Such-Symbol (Lupe) klicken
- Den gesuchten Begriff eingeben
- GitLens zeigt die Commits an, die ihn enthalten

### 6. Markierungen und Lesezeichen
- Wichtige Commits für den schnellen Zugriff markieren
- Lesezeichen für wichtige Stellen im Code setzen
- Änderungen auf bestimmten Branches verfolgen

### 7. Integration mit GitHub/GitLab/Bitbucket
- Pull Requests direkt in VS Code ansehen
- Pull Requests erstellen und reviewen, ohne den Editor zu verlassen
- Kommentare und Diskussionen zu PRs ansehen

## Fortgeschrittene Techniken

### 1. Zusammenarbeit in Echtzeit
- Sehen, wer gerade dieselbe Datei bearbeitet
- Benachrichtigungen, wenn jemand Änderungen auf das Remote pusht
- Unterstützung für Funktionen wie Live Share

### 2. Anpassbare Darstellungen
- Aussehen der Blame-Annotationen anpassen (Farbe, Schrift, Position)
- Eigene Regeln erstellen, um bestimmte Arten von Commits hervorzuheben
- Informationen wie geänderte Zeilen oder betroffene Dateien anzeigen

### 3. Erweiterte Filter und Suche
- Commits nach mehreren Kriterien gleichzeitig suchen (Autor + Datum + Stichwort)
- Commits nach Eigenschaften filtern, etwa Merge-Commits oder Commits mit Issue-Nummer
- Reguläre Ausdrücke in der Suche verwenden

### 4. Integration mit anderen Tools
- Funktioniert gut mit anderen Erweiterungen wie Prettier und ESLint
- Integration mit Aufgabenverwaltungstools wie Jira und Trello
- Unterstützt Workflows wie GitFlow und GitHub Flow

## Best Practices für GitLens

### 1. Blame zum Verstehen nutzen, nicht zum Beschuldigen
- Der Zweck von Blame ist es, den Kontext zu verstehen, nicht einen Schuldigen zu finden
- Wenn du eine seltsame Codezeile siehst, frag „Warum wurde das so geschrieben?“ statt „Wer hat das geschrieben?“

### 2. Mit dem Code-Review kombinieren
- Vor dem Review mit GitLens die vorgenommenen Änderungen verstehen
- Prüfen, wer die wichtigen Änderungen verfasst hat
- Blame nutzen, um im Review gezielte Fragen zu stellen

### 3. Beim Debuggen einsetzen
- Bei einem Fehler mit Blame herausfinden, wann der fehlerhafte Code hinzugefügt wurde
- Verfolgen, wie sich eine Funktion oder Variable im Laufe der Zeit verändert hat
- Den Commit finden, der den Fehler eingeführt hat, um die Ursache zu verstehen

### 4. Performance optimieren
- Bei sehr großen Repositories nicht benötigte Funktionen deaktivieren
- Beim Arbeiten mit Remote-Repositories Caching nutzen, um die Last zu senken
- So konfigurieren, dass nur die benötigte Historie geladen wird statt des gesamten Repositorys

### 5. Projektspezifische Einstellungen
- Projektspezifische Einstellungen in der `.vscode/settings.json` des Workspaces speichern
- Die Konfiguration mit dem Team teilen, um ein einheitliches Erlebnis zu sichern
- Einstellungen an Größe und Komplexität des Repositorys anpassen

## Praxisbeispiele

### Beispiel 1: Die Historie einer wichtigen Funktion verstehen
```javascript
// Herausfinden, wer calculateTotalPrice zuletzt geändert hat
// und warum die Änderung so vorgenommen wurde
function calculateTotalPrice(items) {
  return items.reduce((total, item) => total + item.price * item.quantity, 0);
}
```
- Mit Blame den letzten Commit ansehen, der diese Funktion geändert hat
- Die Commit-Nachricht lesen, um den Grund der Änderung zu verstehen
- Prüfen, ob sie mit einem Issue oder PR verknüpft ist

### Beispiel 2: Toten Code finden
- Mit der Historiensuche herausfinden, wann eine Funktion zuletzt aufgerufen wurde
- Wenn eine Funktion lange nicht aufgerufen wurde, könnte es toter Code sein
- Prüfen, ob es Pläne gibt, sie künftig wieder zu nutzen

### Beispiel 3: Die Entwicklung eines Features verstehen
- Alle Commits zu einem bestimmten Feature verfolgen
- Sehen, wie sich das Feature im Laufe der Zeit entwickelt hat
- Verstehen, welche Designentscheidungen getroffen wurden und warum

## Häufige Probleme beheben

### 1. GitLens zeigt keine Informationen an
- Prüfen, ob Git korrekt installiert und konfiguriert ist
- Sicherstellen, dass du in einem Git-Repository arbeitest
- Das Fenster neu laden (Strg+Umschalt+P → „Reload Window“)

### 2. Langsame Performance bei großen Repositories
- Nicht benötigte Funktionen in den Einstellungen deaktivieren
- Auf die Historie eines bestimmten Commits oder einer Datei fokussieren, statt die gesamte Historie zu laden
- So konfigurieren, dass nur die Historie des aktuellen Branches geladen wird statt aller Branches

### 3. Falsche Blame-Annotationen
- Sicherstellen, dass du die neuesten Änderungen vom Remote gepullt hast
- Auf Probleme mit Zeilenenden prüfen (CRLF vs. LF)
- `git add --renormalize .` ausführen, um die Zeilenenden zu normalisieren

### 4. Kein Zugriff auf das Remote-Repository
- Internetverbindung und Zugriffsrechte auf das Remote prüfen
- Sicherstellen, dass die Zugangsdaten korrekt eingerichtet sind
- `git fetch` manuell ausführen, um die Verbindung zu testen

## GitLens im Vergleich zu anderen Git-Tools

### GitLens Free vs. GitLens Pro
- **GitLens Free**: Bietet die meisten Funktionen, die man für die tägliche Entwicklung braucht
- **GitLens Pro** (kostenpflichtig): Ergänzt Funktionen wie:
  - Erweiterte Blame-Visualisierung
  - Commit-Vorlagen
  - Team-Statistiken
  - Ein Werkzeug zur Lösung von Merge-Konflikten
  - Rebase-Sequencer

### Im Vergleich zu anderen Git-Erweiterungen
- **Git History**: Konzentriert sich auf die Anzeige der Commit-Historie, mit weniger Inline-Funktionen
- **Git Graph**: Ideal zum Anzeigen des Branch-Graphen, aber ohne Blame und Code Lens
- **Integriertes Git in VS Code**: Deckt grundlegende Git-Operationen ab, aber ohne die erweiterten Funktionen von GitLens

## Fazit

GitLens ist nicht einfach nur eine weitere Git-Erweiterung. Es ist ein Werkzeug, das dein Verständnis von Code vertieft und deine Produktivität steigert. Richtig eingesetzt hilft dir GitLens dabei:

- **Weniger Zeit für Kontextsuche**: Statt lange nach dem Hintergrund eines Codeabschnitts zu suchen, siehst du ihn direkt im Editor
- **Bessere Code-Reviews**: Es liefert den Kontext, den du für konstruktives Feedback brauchst
- **Mehr persönliche Wirksamkeit**: Es hilft dir, effizienter zu arbeiten und Professionalität im Team zu zeigen
- **Weiterlernen**: Es ist eine großartige Möglichkeit, Best Practices in Versionsverwaltung und Softwareentwicklung zu lernen

Fang damit an, die Blame-Annotationen einzuschalten und die Grundfunktionen zu erkunden. Sobald du mit GitLens vertraut bist, wirst du dich darauf verlassen, um Code zu verstehen, im Team zusammenzuarbeiten und im Entwicklungsalltag hohe Qualität zu halten.

Denk daran: Das Ziel ist nicht, jede Funktion von GitLens zu kennen, sondern die Funktionen zu nutzen, die am besten zum Workflow und zu den Bedürfnissen von dir und deinem Team passen.

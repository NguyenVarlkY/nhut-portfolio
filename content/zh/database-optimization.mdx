# Deep Dive：数据库深度优化

数据库优化不是“试错”。它是一门关于数据如何在磁盘上存储、读取和加锁（locking）的科学。下面是深入的技术分析。

## 1. B-Tree 内部结构：理解数据结构
索引不只是一个列表。
- **B-Tree 结构：** 一种平衡树，能在 $O(\log n)$ 时间内完成查找、插入和删除。
- **页分裂（Page Split）：** 当一个节点满了，数据库必须将其分裂，这会消耗 I/O 资源。如非必要，避免使用随机 `UUID` 作为主键，因为它比 `Integer Auto-increment` 造成更严重的索引碎片。
- **Fill Factor（填充因子）：** 调整页的填充比例，以优化读写性能。

## 2. 查询规划器与执行计划
始终使用 `EXPLAIN (ANALYZE, BUFFERS)` 来查看：
- **顺序扫描 vs 索引扫描：** 在百万行的表上做 seq scan 是一场灾难。
- **成本估算：** PostgreSQL/Oracle 依靠统计信息（statistics）来推测执行路径。如果统计信息过时（stale），规划器就会选错路径。
- **Nested Loop vs Hash Join：** 在大数据集上，Hash Join 通常比 Nested Loop 更快，但更耗内存。

## 3. 高级 SQL 技巧
### 3.1. 处理大数据量
- **分页：** 对超大数据（数百万行）绝不要使用 `OFFSET/LIMIT`，因为 `OFFSET` 必须扫描之前的所有行。请改用 **Keyset Pagination**（基于上一页最后一行的列值）。
- **分区：** 对于巨型表，按时间分区（例如按月分区），以加快查询并管理旧数据。

### 3.2. 并发控制
- **加锁：** 理解 `Row-level locking` 与 `Table-level locking` 的区别。
- **死锁：** 在高并发环境中，始终按照固定顺序更新资源，以避免死锁。

## 4. 全文检索（FTS）
不要使用 `LIKE '%keyword%'`。
- **为什么？** 它无法使用普通索引（B-Tree）。
- **解决方案：** 使用 **GIN/GiST 索引**（Postgres），或者在需要大规模扩展和复杂搜索（模糊搜索、词干提取）时集成 **ElasticSearch**。

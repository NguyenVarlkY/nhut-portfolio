# 调试的艺术：查找 Bug 的科学方法

人人都能写代码，但资深工程师的不同之处在于 **排查问题（troubleshooting）** 的能力。专业的调试不靠运气或直觉，而是一套建立在科学方法之上的 **系统化流程**。

## 1. 调试中的科学方法

### 1.1 观察（Observation）
第一步也是最重要的一步：**必须能复现 Bug**（reproduce bug）。如果无法复现，就无法修复。

- 准确记录导致 Bug 的操作步骤。
- 记录输入、输出和系统状态。
- 确定环境：哪个浏览器、哪个版本、哪台设备。

### 1.2 假设（Hypothesis）
对 Bug **为什么** 会发生做出有依据的推测。不要瞎猜，而要基于：

- 对代码库的了解。
- 错误信息（error message）。
- 日志和堆栈跟踪。
- 对数据流的理解。

### 1.3 实验（Experiment）
通过以下方式验证假设：
- 在可疑位置添加详细的 **日志**。
- 使用 **调试器** 设置断点，逐步观察。
- **隔离** 代码：临时注释掉、拆出变量、用简单的输入测试。
- 在代码中做 **二分查找**：不断把可疑范围缩小一半。

### 1.4 结论（Conclusion）
找到根本原因并修复，然后 **编写测试**，确保这个 Bug 永远不会再回来（**回归测试**）。

## 2. 高级调试技巧

- **小黄鸭调试法：** 把你的代码讲给一只“橡皮鸭”听——把问题大声说出来，答案往往就会浮现。
- **通过重读代码来调试：** 带着“这行代码实际上做了什么？”而不是“它应该做什么？”的心态逐行重读。
- **使用 Git Bisect：** 通过对提交历史二分查找，定位引入 Bug 的那次提交。
- **检查版本和依赖：** 很多 Bug 来自库版本的变化，而不是你的代码。

## 3. 必备调试工具

- **浏览器 DevTools：** Network 面板、Console、Sources、Performance。
- **服务端：** 日志文件、APM 工具（Datadog、Sentry）、监控。
- **数据库：** 查询日志、EXPLAIN、索引分析。
- **API：** Postman、curl、mock 服务器。

> *"Debugging is twice as hard as writing the code in the first place. Therefore, if you write the code as cleverly as possible, you are, by definition, not smart enough to debug it."* — Brian Kernighan
